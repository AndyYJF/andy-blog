# andy-blog 中英双语国际化实施计划

> 本文为历史版本，已由 [国际化方案 v2](i18n-plan-v2-2026-09-26.md) 替代。后续实施以 v2 为准；本文保留用于对照对抗审查，不再作为当前实施规格。

日期：2026-09-26。状态：规划完成，待实施。本文依据当前本地源码制定，未核查生产内容数量，未实施国际化、修改生产或提交代码。

## 1. 目标与关键选择

用户已明确：**英文界面＋全量文章英文版**。首次上线不以精选文章、英文摘要或浏览器即时翻译替代全文英文。

建议保留现有中文 URL，在同一域名下新增 `/en/`。继续使用 Typecho 编辑、Astro 静态生成、Pagefind 搜索、Waline 评论及现有离机构建与蓝绿发布流程。

核心方案：

1. 中文原文与英文译文由同一 Typecho CID 关联，译文作为持久内容保存到 Typecho。
2. 中文路由、评论标识、现有 feed GUID 保持稳定；英文 URL 从已有规范路由派生。
3. 首次双语上线前完成全部公开文章翻译与校对；上线后按用户已确认的策略执行：**中文先发布，英文异步补齐**，翻译等待或失败不阻塞中文正常发布。
4. 翻译任务独立于站点构建；构建只读取已保存的译文，不临时调用翻译模型。
5. 前端通过共享组件与语言字典渲染，避免复制出两套长期分叉的网站。

“全量文章”定义：发布快照中符合现有公开条件、且 `kind=post` 的所有文章，包括 `allowFeed=false` 的公开文章；草稿、密码保护内容、已撤回和已删除内容不在公开翻译集合中。`allowFeed` 继续仅控制 RSS 与 llms 输出资格。

## 4. URL、路由与语言切换

| 内容 | 中文 | 英文 |
|---|---|---|
| 首页 | `/` | `/en/` |
| 文章列表 | `/posts/` | `/en/posts/` |
| 第 n 页 | `/page/n/` | `/en/page/n/` |
| 文章 | 原 `canonicalPath`，通常 `/posts/<routeId>/` | `/en`＋原 `canonicalPath` |
| 归档 | `/archive/` | `/en/archive/` |
| 分类/标签 | 原规范路径 | `/en`＋原规范路径 |
| 独立页 | `/about/` 等 | `/en/about/` 等 |
| 邀请领取页面 | `/linuxdo/` | `/en/linuxdo/` |
| 文章 RSS | `/rss.xml` | `/en/rss.xml` |
| llms | `/llms.txt`、`/llms-full.txt` | `/en/llms.txt`、`/en/llms-full.txt` |

### 路由实现

- Astro 设置中文为默认语言、默认语言不加前缀，英文文件入口放在 `src/pages/en/`。不引入 SSR 作为国际化前提。
- 保持 `data/route-map.json` 中现有 CID、routeId、canonicalPath 的含义；同步阶段生成独立的语言路由清单，例如 `.cache/i18n-manifest.json`。该清单是派生产物，不建立第二套路由事实来源。
- 建立 `localizedPath()` 与 `alternateFor()`，按已生成的路由清单查找目标。不能对任意 URL 粗暴加 `/en`，尤其是 `/api/`、`/linuxdo/claim`、静态资源和站外链接。
- 预先检查原站是否已占用 `/en/` 命名空间；冲突需明确处理，不能静默覆盖。
- 中文现有 `[...page].astro` 与英文入口明确分工，按实际 canonicalPath 生成路径，避免新 catch-all 抢占固定页。
- 页面保持尾斜杠；英文 RSS/txt 端点无尾斜杠，并扩展项目文档中的端点例外说明。

### 交互规则

- 导航使用文字 `中文 / English`，不使用国旗代替语言。
- 文章切换语言留在同一篇；分类、分页也切换到已存在的对应页。目标不存在时展示明确说明和英文文章列表入口，不伪造对应链接。
- URL 决定语言；不按 IP、浏览器语言或 localStorage 强制跳转，避免访问分享链接时被带走及 CDN 同 URL 混语种。
- 站内正文链接有英文对应页时指向英文；保留外部地址、下载地址和接口地址。
- 标题翻译会改变锚点：构建并检查中英标题锚点映射。能对应时迁移 hash；不能对应时移除无效 hash 并定位正文，不制造失效链接。
- 初版语言切换可使用完整页面导航，保证搜索与评论按新语言重建；同语言导航继续保留现有 View Transitions。

## 5. 内容存储与同步契约

### 推荐：同一 CID 的 Typecho 英文扩展字段

为 Typecho 增加“英文版本”编辑区域，建议使用有版本号的结构化字段 `i18n_en` 存储英文内容，并通过插件界面编辑。沿用同一篇文章的发布权限和身份，不额外创建一篇英文 post。

建议字段契约（待实施，不是当前已有字段）：

```ts
type EnglishTranslation = {
  schemaVersion: 1;
  title: string;
  description: string;
  body: string;
  sourceFormat: 'markdown' | 'html';
  sourceHash: string;
  status: 'draft' | 'reviewed';
  translatedAt: string;
  reviewedAt?: string;
  glossaryVersion: string;
};
```

`sourceHash` 从确定性序列化后的翻译相关源字段计算，至少包括标题、正文、摘要生成所依赖内容及需翻译的自定义说明；排除 modified、译文字段自身和评论开关。中文实质修改后，读取时推导为 stale，而非继续当作 reviewed。共享图片/权限等字段单独继承当前源值；分类译名以稳定 mid 的字典版本跟踪。

实施前确认 `typecho_fields.str_value` 容量、编码、编辑器提交大小以及快照导出支持；用最长文章做一次真实保存与导出回读。若不满足容量和事务要求，再采用专用翻译表，并同步扩展导出器、备份与恢复，不能悄悄截断正文。该选择应在内容模型阶段完成。

### 不选择的替代方案

| 方案 | 本项目不作为首选的原因 |
|---|---|
| 英文作为另一篇普通 Typecho post | 需要改造中文分类、原生列表、feed 与路由分配，易被统计为两篇 |
| 人工维护 Astro 生成目录 | 同步会覆盖，与现有内容源约定冲突 |
| Git 中另维护一套正式译文 | 让内容编辑跨两个系统，原文撤回与译文发布更难保持一致 |
| 访问时在线机器翻译 | SEO、缓存、延迟和翻译稳定性难以保证 |

### Astro 数据契约

- 现有中文集合保持原内容 ID，增加默认 `locale: 'zh-CN'`，保持兼容。
- 英文同步到独立生成目录并定义独立集合，例如 `postTranslations`、`pageTranslations`；首版避免直接混入原 posts/pages 集合。
- 英文条目包含 `locale: 'en'`、`sourceCid`、`sourceEntryId`、`translationKey`、`sourceHash`、`translatedAt`，并继承当前 `allowComment`、`allowFeed`、cover、分类/标签标识。
- 同一文章 `translationKey` 可采用 `post:<CID>`；英文 `canonicalPath` 独立，`commentKey` 沿用中文，英文 `feedGuid` 使用稳定的英文 URL 或固定语言后缀，不能包含内容 hash。
- 英文摘要使用独立长度策略，例如建议 50–180 字符；中文保留 24–180 字符约束。标题/正文缺失、非法格式、无法解析的译文字段必须报告具体 CID。
- 同步先校验原文与各条译文，再写暂存产物并替换输出。日常发布中缺译、stale 或单条译文格式错误只影响对应英文输出，记录 CID 与原因，不阻塞有效中文内容。基础快照损坏、路径冲突及无法安全生成产物仍是构建失败。失败不得清空当前生成内容。`CONTENT_BACKUP_DIR` 继续只写备份，不修改正式路由表。
- 翻译存储区分工作草稿与最后一次有效校对版本；上面的 EnglishTranslation 是单个版本的结构，不意味着草稿可以覆盖已发布版本。用独立字段或版本记录保存两者，构建从 Typecho 快照读取明确版本，不从旧 dist 拼接英文内容。
- 原文撤回、设密码或删除时，译文一起退出生成、索引、feed 与语言映射。重新发布使用原 ID，不重新分配英文地址。

CMS 插件保存译文需权限检查、CSRF 防护、输入大小校验和乐观版本检查；翻译任务不得绕开 Typecho 发布权限直接标记正式发布。两种语言继续走 raw → sanitize 等原有渲染管线。

## 6. 全量翻译与持续更新

### 首次迁移

1. 固定一份最新公开内容快照，导出 CID、标题、字数、格式、短代码与图片数量，生成翻译清单。
2. 建立术语表：VPS、BGP、DN42、ASN、路由宣告、隧道、回源等；明确作者口吻、标题格式、专名保留规则。
3. 选 2–3 篇结构不同的文章校准流程，至少涵盖长代码、图表/公式、短代码或 HTML 原文；随后覆盖清单全部文章，试译不缩减最终范围。
4. 采用结构化分段翻译，保护代码围栏、行内代码、链接目标、公式、短代码 ID 和机器参数；使用原始 Markdown/HTML，不反向抓渲染页作为正式源。
5. 机器翻译可生成初稿，但逐篇检查技术含义、命令语义、遗漏段落、数字、链接和图注。作者原本不确定的判断不能被译为肯定结论。
6. 经授权后导入 Typecho；保存译文及对应源 hash。源已改变时拒绝覆盖，重新生成差异任务。
7. 最新候选快照中，全部公开文章均有 reviewed 且 sourceHash 匹配的英文版本，才能称为全量就绪。

若采用外部翻译 API，供应商、模型、预算和数据发送范围在实施时确定；本轮不调用付费翻译。任务支持按 CID/hash 断点续跑、限流、失败重试和成本记录。构建阶段不联网重新翻译。

### 新增与更新文章：已确定中文先发、英文异步补齐

用户已明确选择此策略。中文沿用现有发布流程，不等待翻译；“全量英文”是首次上线标准和持续覆盖目标，不是每次中文发布的同步前提。

```text
Typecho 发布或修改中文
  ├─ AutoRebuild → 最新快照 → 离机构建 → 发布中文及当前可用英文
  └─ 持久翻译任务 → 生成英文草稿 → 校对并校验源 hash
       → 保存有效英文版本 → AutoRebuild → 最新快照 → 重建并补齐英文
```

两条路径独立：翻译入队或 API 失败不撤销中文发布，不让中文构建等待外部模型。中文内容变化时记入持久待译状态；用补偿扫描找回漏入队任务。沿用既有构建锁及 pending/dirty 合并机制，译文完成事件不另起并发发布流程。

| 当前状态 | 中文站 | 英文站与切换入口 |
|---|---|---|
| 新文章，无有效译文 | 正常发布；显示“英文翻译准备中” | 不生成英文详情或伪英文占位页，不进入英文列表/索引 |
| 已有英文，中文更新 | 新中文正常发布 | 保留上一次有效英文，并提示“中文原文已更新，此译文待更新”，显示译文版本时间及原文链接；切换入口标注旧译文 |
| 译文完成并通过校对 | 中文不受影响 | hash 匹配当前源后保存，通过下一次成功 release 更新英文页面和索引 |
| 翻译失败或格式错误 | 正常发布；后台显示失败及重试入口 | 有可验证旧版本则按旧译文规则保留，否则不生成；不公开草稿或损坏内容 |
| 原文撤回、删除或设密码 | 下线或按原有规则处理 | 同次发布移除所有英文版本、语言关系、索引与订阅，刷新旧 URL |

旧译文不冒充最新等价版本：标记 noindex，暂不进入英文列表、搜索、sitemap、RSS/llms 或双向 hreflang；直接访问已有 URL 时仍可阅读带说明的旧版本。新版就绪后恢复正常收录。旧译文更新时间保持原值，不改成中文修改时间。涉及敏感信息或严重技术错误时，编辑可单独停用英文旧版本，优先下线而非继续展示。

任务使用 `CID + 目标语言 + sourceHash + glossaryVersion` 去重。每次回写时重新检查文章可见性和当前源 hash；过期任务标记 superseded，不覆盖新版本、不触发无效发布。供应商或模型版本变更仅在显式重译时作为任务修订记录，避免自动重跑全站。任务与回写支持幂等重试，重试耗尽留在失败队列；不因失败静默放弃全量覆盖目标。

翻译内容状态 missing/draft/reviewed/stale 与任务 queued/running/failed/superseded 分开记录。后台分别显示“中文构建中/已上线”“英文待译/待校对/待发布/已上线”；只有对应版本进入成功切换的 release 后才标为已上线，不能将保存成功、入队成功当作发布成功。首次要求 100% 就绪，日常报告覆盖率、缺译数、stale 数及最久等待时间，不把允许滞后解读为永久不翻译。

**撤回与安全删除优先**：始终以最新快照的可见性和权限为准，翻译等待不能阻塞撤回。运行中的任务在回写前发现撤回则取消，禁止在后续英文重建时复活内容。已有构建若基于过期快照，发布协调器在切换前检查撤回/权限修订；丢弃过期候选并重建，不能先切换再依赖下一次构建修复。此前已发布的文件由移除后的 release 和 CDN 刷新共同清除。

AutoRebuild 保持唯一发布触发入口。英文有效版本完成后发送幂等的内容变更事件，沿用构建任务合并与失败重试机制；普通草稿保存不重复触发。原文 hash 排除译文字段与保存时间，避免“保存译文 → 判断原文过期 → 再翻译”的循环。CMS 预览理解英文草稿与旧译文，但不把未校对版本暴露为公开页。

## 7. 前端改造

新增 `astro/src/i18n/`：语言类型、中文/英文字典、页面路径映射、日期/数字格式化。通过明确的 locale 参数传递到布局和组件；不要让组件各自猜测路径。

| 区域 | 改造内容 |
|---|---|
| BaseLayout / CommonHead | lang、标题、description、导航、页脚、aria 文案、canonical、alternate、OG、JSON-LD |
| 首页 / profile / AboutProfile | 人物简介、项目描述、按钮文字、可访问标签；沿用相同事实与视觉结构 |
| PostList / Pagination / 文章模板 | 文案字典、当前语言链接、前后篇和相关文章按语言筛选 |
| SearchDialog | 提示、错误、加载状态、搜索语言和切换时实例销毁 |
| Comments / readonly-comments | Waline 语言及只读模式提示、日期、空状态；原评论内容不改 |
| ListeningPage / directive 插件 | 播放按钮、展开文案、note 与可访问描述；保持平台原生内容 |
| linuxdo 页面 | 全部前端状态和 Turnstile locale；不输出邀请 URL，不改变领取接口 |
| 阅读元信息 | 中文保留字数，英文按词数；暂定 220 words/min 为产品估算参数，最低 1 分钟 |
| 渲染插件 | 代码复制、标题锚点 aria-label、图表预览、表格等交互提示跟随语言 |

构建期插件必须拿到文档 locale。尤其 Expressive Code 和 heading 插件不能通过修改全局默认语言来影响同次构建中的中文页；先确认所装版本的逐文档配置能力，再接入适配层。

英文较长的导航和按钮需检查窄屏换行、弹窗高度和长 URL；保持系统字体、亮暗主题、reduced-motion，以及当前视觉风格。

## 8. 搜索、SEO、评论与订阅

### 搜索

移除全站构建的 `--force-language zh`，让 Pagefind 按 `<html lang>` 分语言建索引。客户端按当前语言初始化，核实 `zh-CN` 在实际产物中的语言键，不假定一定为 `zh`。

中文搜中文，英文搜英文；两种语言共享静态 `/pagefind/` 资源目录。切换语言后的搜索实例必须重建，不能复用旧语言状态。只对正文与需要检索的独立页建索引；邀请页和错误页显式排除。

这是 Pagefind 官方支持的机制；本项目仍需通过实际构建和查询确认现有旧版 UI 初始化参数的兼容性。[Pagefind 多语言文档](https://pagefind.app/docs/multilingual/)

### SEO

- 中英文各自 canonical 指向自己，英文不能 canonical 到中文。
- 等价页面输出相同的一组双向 `hreflang="zh-CN"`、`hreflang="en"`，包含自身；`x-default` 指向对应中文页。只引用真实存在且可索引的等价页。
- HTML lang、OG locale 及 alternate、JSON-LD `inLanguage` 和描述跟随内容语言。英文 OG 可统一采用 `en_US` 格式值，正文风格仍以通用技术英语为准。
- Sitemap 收录双语规范页面；继续排除 RSS、txt、404、邀请页及不可发现分类，并覆盖英文对应地址。可由同一语言映射生成 sitemap alternate，避免手写两份关系。
- 英文 lastmod 反映该译文最近有效修改时间；保存无实质变化不批量刷新全部文章。保留原文发布时间，并单独展示翻译更新时间，避免把旧文章翻译误说成新原创。
- 分享图沿用 Typecho `thumb` 或 `/og-default.png`，本轮不新增逐篇英文分享图。

语言标注关系采用 Google 的等价页面规则；有效翻译与互相引用比机械添加前缀重要。[Google 多语言页面说明](https://developers.google.com/search/docs/specialty/international/localized-versions)

### 评论

推荐双语共用已有 `commentKey`，保留历史讨论，也不要求迁移评论数据库。前端界面按语言显示，明确讨论区可含两种语言。权限沿用源文章的 allowComment 和 release 写入开关；英文路径不能绕开写入策略。

### RSS 与 llms

中文订阅继续只输出中文，新增 `/en/rss.xml`、`/en/llms.txt`、`/en/llms-full.txt`；仅包含允许订阅的英文文章。已有中文 GUID 不变，英文使用稳定独立 GUID。

译文沿用原文发布时间并提供稳定链接；翻译更新不变更 GUID、不把全部历史文章时间改成迁移日。英文 llms 文案英文，仅在索引中以中文标识提供闲话入口，不输出闲话正文。robots 注释补上英文 llms 地址。

## 9. 构建、CDN 与回滚

1. 快照导出、fixture、CMS 预览及正式 sync 使用同一翻译字段契约；英文清单进入 release manifest 与 checksum 覆盖。
   首次启用双语需检查全量 reviewed 且源 hash 匹配；启用后切为日常异步策略，不能继续用“缺译即整站构建失败”。manifest 同时记录各语言已发布源版本及待译状态，用于后台回执、状态展示和防止过期候选覆盖。
2. 新固定 URL 同步维护 `cdn-purge-core.js`、`generate-cdn-preheat-plan.js` 和 `stage4-gate.js`；同时更新英文端点 sitemap 排除。
3. 动态英文文章、分类和分页从 manifest 发现，不能只增加 `/en/` 首页。
4. CDN 刷新集合包含上一次与本次 release 的 URL 并集，覆盖消失的英文详情和最后一页；预热仅限本次真实 200 规范页面。Pagefind 资源失效沿用并核查现有资源策略。
5. `/en/linuxdo/` 与原领取页一样不预热或缓存领取结果；API 始终走原路径和现有验证逻辑。确认请求来源策略没有误拒英文页面，不放宽验证码验证。
6. 继续离机构建，保留图片尺寸和 Mermaid 缓存；实际测量双语后的耗时、内存与包大小，不预先承诺“正好翻倍”。
7. 候选失败不切换。上线与 CDN 操作在后续实施会话取得明确授权；保留旧 release 和 Typecho 译文字段备份。
8. 回滚可切回上一完整 release，但若它包含刚撤回内容，应生成保留撤回状态的修复候选，不能直接恢复敏感旧内容。译文字段可保留在 Typecho，旧前端忽略它们；无需删数据回滚。

## 10. 分阶段实施与完成标准

| 阶段 | 主要交付 | 完成标准 | 工程估算 |
|---|---|---|---|
| P0 内容与路由清单 | 最新快照统计、术语表、命名空间与翻译字段容量确认 | 全量公开文章范围可计算，最长文本回读可行 | 0.5–1 人日 |
| P1 内容链路 | Typecho 英文编辑区域、版本保存、任务队列/补偿扫描、导出、hash、sync 和集合 | 中文独立发布；翻译可重试；英文完成后重建；旧任务与撤回处理正确 | 3–5 人日 |
| P2 页面与交互 | 共享模板、字典、语言切换、英文路由、英文搜索/评论 UI | 两种语言页面与交互连贯，中文旧链接保持 | 2–3 人日 |
| P3 全量翻译 | 所有文章英文正文与页面文案，覆盖报告 | 最新快照文章覆盖率 100%，逐篇完成技术校对 | 按内容量单独估算 |
| P4 SEO 与发布接入 | alternate、RSS/llms、sitemap、CDN 清单、针对性验证 | 产物语义正确，缓存刷新包含撤回 URL | 1–2 人日 |
| P5 候选与上线 | 浏览器验收、候选构建、授权后上线核验 | 中英公网正文/元数据正确，可回滚 | 0.5–1 人日 |

工程合计约 **7–12 人日，另加全文翻译与校对时间**，是基于当前代码的粗估，不是排期承诺。相比初稿增加了异步任务、补偿、版本状态与发布回执的工作量。若 Typecho 字段容量或事务能力迫使采用独立表，需要重新估算 P1。

翻译排期先用试译测量：`总校对时间 = 各类文章字数 × 实测每千字校对时间 + 图表/截图专项时间`。费用依据实际供应商输入/输出 token 和重试量计算；不以本地 12 篇直接推断生产成本。

依赖顺序：P0 → P1 → P2/P3 → P4 → P5。试译校准可在 P1 时开始；全部译文就绪前不对外称为完整英文站。

## 11. 有针对性的验证

本轮仅规划，不运行站点构建或原有全套门禁。实施时针对改动验证下列行为：

| 层次 | 核心用例 |
|---|---|
| 内容模型 | 缺译、旧 hash、非法 JSON 不阻塞中文；可验证旧译文带状态展示；草稿、损坏译文、密码内容不会公开；最长文章/HTML/短代码正常 |
| 同步生命周期 | 中文先发布→译文完成→第二次构建；中文修改→stale 提示→英文补齐；撤回→译文移除；重新发布 ID 不变；草稿不覆盖有效旧译文 |
| 异步任务 | 入队失败补偿、API 失败重试、重复事件去重、任务乱序完成、保存时源 hash 变化、完成事件到达构建过程中仍有下一次重建 |
| 发布优先级 | 翻译失败不阻塞中文新文章和撤回；运行任务及过期构建候选不能复活撤回内容；英文发布失败不撤回已成功中文 release |
| 路由 | 首次每篇源 CID 恰好一个有效英文版本；日常允许待译但不产生死链接；中文 URL 不变；slug 改动不重分配已有 routeId；无 `/en/en/` 和路径冲突 |
| 结构保持 | 段落/标题没有遗漏；代码、数字、URL、公式、短代码参数未被翻译破坏 |
| 构建产物 | 双语 HTML、canonical、hreflang、sitemap、RSS GUID、allowFeed、英文 llms 正确 |
| 搜索 | 中英文真实关键词、无结果、加载失败重试、语言切换后重新搜索，索引不串语言 |
| 浏览器 | 桌面与 390px/320px、亮暗主题；导航、语言切换、分页、目录/hash、复制、图表、评论与返回操作 |
| 邀请页 | 本地/隔离环境验证英文状态与原 API 参数；不靠消耗真实邀请做测试 |
| CDN | current/previous URL 并集包含已移除英文页；固定页齐全；禁预热端点无误 |

运行受影响的同步/路由测试；修改 llms 后运行对应测试；dist 存在后执行 `node scripts/stage4-gate.js`；修改 CDN 固定列表后运行 `npm run cdn:purge:test` 与 `npm run cdn:aliyun:test`。正式候选使用既有发布流水线要求的检查，不额外创建一套重复大门禁。

全量验收报告至少输出：源快照标识、应翻译文章数、有效英文数、缺失数、stale 数、未校对数、撤回残留数，以及人工校对清单。文件数量相等或构建通过不等于翻译质量通过。

## 12. 实施前的默认建议与待定项

已确定：中英双语方向、英文界面、全量公开文章全文翻译；首次历史内容全量就绪，后续**中文先发布、英文异步补齐**，中文发布不等待翻译。

建议按本文推进的默认项：中文 URL 不变；英文 `/en/`；同 CID 存译文；共用评论；静态生成；不强制语言跳转；闲话本期保持中文。

实施时需确定但不阻塞本计划交付的事项：

- 翻译初稿由谁/哪个服务生成，预算上限，以及技术校对责任人。
- Typecho 字段真实容量与编辑能力，最长文章是否满足；根据证据确定最终存储。
